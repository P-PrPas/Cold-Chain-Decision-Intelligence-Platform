# Docker footprint and local recovery

Measured with the same Docker Desktop image-size reporting on Windows, 2026-11-11:

| Image | Before | After | Change |
| --- | ---: | ---: | ---: |
| Web | 960 MB | 266 MB | -72% |
| API (also worker/storage-init) | 433 MB | 367 MB | -15% |
| Development S3 emulator | 561 MB | 286 MB | -49% |

These are Docker's reported image sizes, not independent physical allocations. Shared layers are counted once on disk. API, worker and bucket initialization now reference the same image. PostgreSQL, Redis and Keycloak are third-party runtime services, not bundled into the web image.

## Causes and changes

The old web runtime copied the entire build directory and installed production node_modules (approximately 487 MiB inside the container), rather than a traced runtime. Each rebuild retained another large build-cache layer. Build cache had accumulated to 17.48 GB; deleting application records alone would not have solved that.

The web now runs Next.js standalone `server.js`, plus static/public assets, as the non-root node user. Source, TypeScript tooling, the complete dependency tree and build caches stay out of the runtime. This SVG/WebGL UI does not use server image transformation: `images.unoptimized` is explicit and unused Sharp/native image libraries are removed from the standalone output. Restore those dependencies and image optimization together if a future feature requires `/_next/image`.

Python installs omit generated bytecode and pip caches. Runtime dependencies needed for CSV, QA, reports and storage remain intact. The development Moto server installs S3 plus Flask/CORS, rather than the server extra's unrelated CloudFormation and AWS emulator dependencies. This is a development S3 emulator, not a production object-store recommendation.

Docker contexts exclude tests, local dependencies, caches, environment files and generated output. Runtime dependencies are installed before source COPY, preserving reuse when only application code changes. Node's executable and Python/native runtime dependencies remain; removing them would break the application rather than optimize it.

## Cleanup performed with owner authorization

All pre-existing Docker volumes were removed, including those belonging to other local projects. Containers holding those volumes were removed as required. Docker reported 2.221 GB reclaimed from volumes and 17.48 GB from build cache. This permanently removed their stored data. Starting the validated stack subsequently created fresh PostgreSQL/Redis storage; original data was not restored.

Deleting Docker content freed blocks inside the Linux disk, but Windows C: initially still had only approximately 150 MB free. Docker was stopped and its verified `docker_data.vhdx` was compacted with Windows DiskPart using Administrator consent. C: then had approximately 17.1 GB free before rebuilding. The original VHDX was 29.2 GB. DiskPart compact is documented by [Microsoft](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/compact-vdisk); never compact an active read/write virtual disk.

## Keep rebuilds bounded

Use `docker system df -v` to distinguish volumes, images and build cache. After a series of builds, `docker buildx prune --force --max-used-space 2GB --reserved-space 512MB` can bound **reclaimable cache** on the shared builder; it may make other projects' next builds slower. It does not delete volumes or source files. The retained limit is a cleanup target, not a hard maximum during a build. Post-verification cache was approximately 2 GB in this session.

Do not routinely use `compose down --volumes` or volume prune: those delete application data. The reset in this session was explicitly requested by the owner. Docker Desktop's RAM figures in the container list are not disk usage. Host free space can differ from Docker's reclaimed-space report because of VHD allocation and shared/compressed layers.

Verification includes production build/health checks and the complete OIDC → CSV → policy → analysis → simulation → independent QA → private PDF browser workflow, exercising the slimmer S3 emulator and web runtime.
